# Dispatch

Run several workers on one repo without collisions. Dispatch plans **waves**: tickets in one wave touch no shared hotspot, so their PRs merge cleanly; a colliding ticket waits for a later wave. Each worker gets a **self-contained prompt** for a Claude, Codex or Mistral thread: no skill names, every command spelled out.

Dispatch plans and launches; it never builds a ticket. It writes to the tracker only in steps 6–8 and opens a PR only for the areas map, when asked. `docs/agents/issue-tracker.md` is the source for labels, Claim and Release commands and the Parallel work fields: read it whole first. Ticket numbers read the same bare or as `#<n>`.

## Steps

1. **Check the tracker.** When the doc is missing or describes the local tracker, stop: parallel workers need GitHub, because local claims stay invisible to other threads until they merge. Suggest one `/build-this` thread on the tickets, and `/setup:setup-pluneto-skills` to switch trackers. Then run the doc's Model database command and keep its table (task types to provider, model, effort). Blank, or old default text starting `[blank:`, means the shared table: `gh api repos/PlunetoD/t3-retro/contents/models.md --jq .content | base64 -d`. `none` means no table: note "model database: none" for the tracking issue and use Model tiers for every ticket; a failing command does the same with "model database unreadable". Done when the doc is a GitHub tracker and you hold every field later steps use (blank fields mean their fallbacks).

2. **List the tickets.** `gh issue list --state open --label "<agent label>" --json number,title,body,url,labels --limit 200` (only the issues the user named, if any; for `milestone "<name>"`, add `--milestone "<name>"`). Leave out issues with the draft or planned label: they are not tickets yet (a named draft gets the pointer `/plan-this issues <n>`). Run the doc's winner command on each: a live claim means taken, so leave it out of the waves. Get each ticket's open blockers (the doc's **Count open blockers**, or its `Blocked by` line) and list open `<human label>` issues separately. Done when every open agent ticket is free or taken, with its blockers.

3. **Map the areas.** Read the Areas map if it exists: areas to paths, **hotspots** (files many tickets edit: generated types, shared registries, lockfiles, top-level docs) and **shared functions** (SQL functions several migrations redefine). Without it, infer: hotspots are files in many merges of `git log --name-only --format='--%h %s' -n 300` (distinct commits per file), areas are the folders the tickets name. Write each free ticket's areas, likely hotspots and shared functions, counting a doubtful hotspot as touched (a later wave costs minutes, a conflict costs a human). Done when each has them, marked "map" or "inferred".

4. **Plan the waves.** Take free tickets in blocker order, then by priority (high first, then normal, low last; a ticket counts at the highest of its own priority and that of every ticket it blocks, directly or through others), then by number; a low ticket goes no earlier than the last wave holding a high or normal ticket. Put each in the first wave after all its blockers' waves in this batch that holds no ticket sharing a hotspot or shared function with it and has fewer than Max workers tickets (sharing an area alone is fine). A ticket whose open blocker is outside the batch goes in no wave: list it as blocked.

   Pick each waved ticket's worker from the model table **task type** that fits its title, body and areas: the type's rank-1 row gives provider, model and effort (`picked from: <type> rank 1`). A row whose model is on the exclusion list in the table's header (`claude-fable-*`) is skipped as if absent. A ticket fitting no type, and every ticket when the table is unreadable, gets a **tier** on Claude (pool), model from the Model tiers line (blank: its default), `picked from: tiers`: **strong** at high effort for a migration, shared function, auth or permissions, payments, concurrency or hotspot; **light** at low effort for new files or mechanical changes; **standard** at medium effort otherwise. A ticket needing a new raster image (not SVG or logo fixes) takes the `image generation` row; if that is unavailable or the table unreadable, give it its other work's row and mark it **image**: its worker parks on the image as a user decision. The **reviewer** is a provider different from the worker's, taken at that provider's `review` row: a Mistral worker's reviewer is Claude (pool) (Mistral never reviews), a Claude worker's is Codex, a Codex worker's is Claude (pool); no such row: that provider's strong tier at high effort. Done when every free ticket is in one wave or listed as blocked, no wave holds two tickets sharing a hotspot or function, and every waved ticket has provider, model (or "default"), effort, picked-from note and reviewer.

5. **Write the prompts.** Fill every `<…>` field of [worker-prompt.md](worker-prompt.md) for each waved ticket from the doc, the repo (`gh repo view --json nameWithOwner,defaultBranchRef`) and the steps above. Branch: `t3/<n>-<slug>`, two to four lowercase key words of the title, hyphenated, no articles or prepositions (`t3/41-sponsor-entity`). Check commands: those the repo's `AGENTS.md` names, else package scripts or Makefile targets. Main health: the doc's command when it is custom; blank, or old default text starting `[blank:`, means [main-health.md](main-health.md)'s command with `<default branch>` filled. Reviewer: `<provider> <model>, <effort>`, with the Review command for its provider and `<dir>` = `/tmp/review-<n>`. `<owner>`: the doc's Decision owner, else `gh repo view --json owner --jq .owner.login`. Sub-agent models, for the worker's provider: Claude `<light model>` = `haiku`, `<standard model>` = `sonnet` (the Agent tool takes only these aliases); Codex the Model tiers line's light and standard models (blank: "your smallest model" and "your default model"); Mistral workers get no sub-agent model lines: drop both the Light and Standard lines and the "Save your context" paragraph's model references (keep the prompt's bracketed Mistral note); they do the work themselves. A sub-agent never runs above its worker: for a worker below its provider's standard model (the light tier included), drop the Standard line. Done when `grep -nE 'CLAUDE\.md|(^|[[:space:]])/[a-z][a-z-]*([[:space:]]|$)|(workflow|engineering|skill-tools|design|setup):[a-z-]+|[Ss]kill[[:space:]]' <prompts>` has no hit that tells the worker to load a skill, run a slash command or read `CLAUDE.md` (a Codex or Mistral worker can do none; the check covers Mistral prompts too); a hit inside a repo name, path or check command is fine, rewrite the rest as the plain command or rule.

6. **Write the tracking issue.** Create one unlabelled issue with the task type (`--type`, the doc's **Issue types**) titled `Batch YYYY-MM-DD` (` (2)` if that title exists), put its number in each prompt's `<batch>`, and write the body with `gh issue edit --body-file`: one checklist per wave (`- [ ] #<n> <title> · <areas> · <provider>: <model> · <effort> · picked from: <type> rank 1 (or tiers) · review: <reviewer> · waits on #<m>`, plus ` · image`; `<provider>` is the provider's display name), then the blocked, taken and human tickets one line each, then each prompt in a fenced block under `### #<n>`. Note above the checklists if the model table was unreadable. Done when every waved ticket has its line and prompt.

7. **List the loose ends.** **High priority**, at the top: open high-labelled issues in no wave (blocked, taken, human or not named), each with why. **Stale claims**: open issues with the claim label whose winning claim comment is over a day old and that have no open PR (none from `gh pr list --state open --json number,headRefName,body` whose branch starts with `t3/<n>-` or whose body says `#<n>`), each with the doc's release command; a claim label with no live claim is stale too, a decision-labelled issue is parked, not stale. **Waiting on the user**: open decision-labelled issues (with the newest comment's URL, the question) and any open `Main is red` issue (fix-ladder.md's listing). **Areas map**: when step 3 inferred anything, offer it as a docs-only PR (`docs/agents/areas.md` on `docs/areas-YYYY-MM-DD`; the user merges). Done when all four lists are in the tracking issue (or "none").

8. **Wait for the word, then launch.** End with a plain message, not a question tool (a question card in a T3 thread breaks when the user types into the thread): the waves as a table, the tracking issue link, the loose ends, and the replies that act, with bare ticket numbers (T3's composer turns a typed `#<n>` into a pull-request chip):
   - `launch wave <N>`: one wave, then wait for the next reply.
   - `launch waves <A>-<B> merge if green` or `launch all waves merge if green`: a chain.
   - `merge if green` on a single wave lets its workers merge.
   - Per-ticket overrides: `<n> on codex`, `<n> on mistral` or `<n> on claude` (provider), `<n> strong` (tier), `<n> high` (effort), `<n> <model id>` (model).
   - `open the map PR`.

   Launch nothing until the user replies `launch wave <N>`, `launch waves <A>-<B>` or `launch all waves`. A pull-request reference where a ticket number belongs: launch nothing, name the PR and ask for bare numbers. A chain needs `merge if green` in the same reply (each wave starts only once earlier tickets are closed, which needs merged PRs); without it, launch nothing and ask for `launch waves <A>-<B> merge if green` or `launch wave <A>`. Then:
   - A wave starts once every earlier ticket is closed and no `Main is red` issue is open (fix-ladder.md's listing); otherwise name what is open and wait. Tick closed tickets' lines in the tracking issue.
   - Load **t3-orchestration**. Read the live model catalog once with `orchestrator_capabilities` and write a `## Model database` section in the tracking issue: the table's models the catalog no longer lists, and catalog models of every enabled provider (Mistral Vibe included) with no row, leaving out models on the exclusion list (`claude-fable-*`, per the table's header) (or "all rows live"). A row **can launch** when its model is in the catalog and its provider is enabled and installed.
   - Apply the reply's overrides per ticket. A provider override takes that provider's rank-1 row for the ticket's type, else its first rank-2 row (in table order) that can launch; none: that provider's tier. A tier word takes that tier's model from the provider's Model tiers line; `<n> <model id>` and `<n> high` set model and effort directly. Never pick or accept an excluded model (`claude-fable-*`): an override naming one is refused (name the model, say it is excluded, and keep the ticket's pick).
   - A worker row that cannot launch (model missing from the catalog, provider disabled or not installed) falls back: take the type's first rank-2 row, in table order, whose provider and model can both launch, skipping every row of the unavailable provider (not only the missing model). A row from the Model tiers line (tier tickets) is unchanged: a missing model falls back to the provider's default. No rank-2 row can launch: use that ticket's tier on Claude (pool). Note each fallback in the ticket's launch comment (`fell back from <provider> <model>: <reason>`). A missing effort goes to the nearest one the model advertises (for Mistral, the values of its `thinking` option), also noted in the launch comment.
   - After any fallback or override, recompute the reviewer: a provider different from the final worker's, at its `review` row (step 4), and refill the prompt's `<reviewer>` and Review command (step 5). Run this once the worker's provider and model are final, before the sub-agent model refill. A reviewer that cannot launch (model missing from the catalog, provider disabled or not installed) is not replaced by a tier on the worker's provider: take another provider that can launch at its `review` row, different from the worker's, never Mistral; none left: the ticket does not launch, and its comment on the tracking issue says why (no independent reviewer available). The reviewer's effort follows the same nearest-effort rule. Then refill the prompt's `<light model>` and `<standard model>` and re-apply the cap (step 5).
   - For each ticket, rerun the winner command (skip if now taken), then `t3_thread_launch` with the ticket's prompt (last line `merge if green` when the user said so), a worktree strategy (`baseRef` the default branch, `branch` `t3/<n>-<slug>`, `startFromOrigin: true`), title `#<n> <title>`, and the ticket's provider, model and effort option (Claude `effort`; Codex `reasoningEffort`; Mistral (`acpRegistry_mistral_vibe`) `thinking` set to the row's effort (low, medium or high), plus `mode: auto-approve`). Check each option name against the tool's schema from `orchestrator_capabilities`. Without that tool, say so and point to the prompts in the tracking issue: the user pastes each into a new thread on its branch.

   Done when every ticket in the wave has a comment on the tracking issue (`#<n> → thread <id> (<provider display name>, <model>, <effort>), branch <branch>`, e.g. `#<n> → thread <id> (Mistral Vibe (mine), zai-glm-5-3-flash, medium), branch <branch>`; a fallback note goes after the branch: `, branch <branch>; fell back from <provider> <model>: <reason>`), a not-launched note, or the user has been pointed to the prompts.

   **Watch the wave**, after every launch, single or chained: stay in the turn and wait on the wave's threads with `t3_thread_wait`, one at a time with `untilDelegatedWorkSettled` and a 10-minute timeout, again after each timeout (this loop overrides t3-orchestration's end-the-turn rule). After every return run Main health (step 5) and tick closed lines. The wave **settles** when each worker thread has finished its turn (a merging worker finishes only after triaging its merge's main run) or is parked on the decision label, no Red-main repair is running, and a last Main health prints `green` (`pending` keeps the loop going); a stall (see Chaining) ends the watch early, in a single wave too. Without `t3_thread_launch` there is nothing to watch: the user pasted the prompts.

   **Red main** (Main health prints `red <url>`, or a `Main is red` issue is open) is repaired at once, in any launch: follow [fix-ladder.md](../build-this/fix-ladder.md)'s Red main. Its go-ahead is this launch, `merge if green` or not, unless the repo owner's rule (`AGENTS.md`, `CLAUDE.md`) asks more before an agent merges; then the fixer opens its PR without merging, and you post its URL for the user to merge and keep watching. `t3_thread_launch` each fixer thread: a self-contained prompt with the ladder's fixer brief plus push, PR and merge as worker-prompt steps 8 to 11 (last line `merge if green` when it may merge), and the worktree strategy above with `branch` `t3/fix-main-<short sha>-<tier>`. Resume once the issue holds the ladder's Confirm comment (`released: done in #<pr>`) or is closed by the merged fix, and Main health prints `green`, then `t3_thread_send` "main is green, land again" to each worker that commented `waiting on main`.

   **A single wave**, once settled: report it (closed tickets, parked questions with their URLs, open PRs) and wait for the next reply: `launch wave <N+1>`, or `status`, which ticks every line whose issue is closed, lists the high-priority issues in no wave and what waits on the user (step 7) and closes the tracking issue once every line is ticked.

   **Chaining** (`launch waves <A>-<B>`, `launch all waves`): launch wave A; each time a wave settles, read each ticket's state (`gh issue view <n> --json state`), tick closed lines and launch the next wave, until wave B has settled. The chain **stops at the first stall** and reports it plainly (no question tool): a ticket parked on the decision label (with its question's URL), a red main whose strong fixer failed, or a worker thread that finished with its issue open and not `waiting on main`. `launch wave <N>` or a new chain then continues from the wave named.
